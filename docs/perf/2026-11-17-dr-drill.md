# Báo cáo — drill sự cố, khôi phục và SLO (B6, 2026-11-17)

Câu hỏi: hành vi khi Redis, Postgres, Kafka chết có đúng như tài liệu không, sao lưu có khôi phục được nguyên vẹn không, và SLO đặt ra
có cảnh báo tương ứng không?

## Môi trường

Laptop Windows 11, Docker Desktop, các container compose dev. **Không có staging** (không có máy hay hạ tầng riêng), nên mọi thứ
dưới đây là drill cục bộ. Dữ liệu: [data/2026-11-17-b6](data/2026-11-17-b6/).

## Drill chết hạ tầng (API build thật chạy ở cổng 4100, dừng container thật)

| Drill (`pnpm --filter api drill:…`) | Kết quả | Khớp [failure-modes.md](../runbook/failure-modes.md)?                                                            |
| ----------------------------------- | ------- | ---------------------------------------------------------------------------------------------------------------- |
| `redis`                             | 12/12   | Có: `/ready` 200 `degraded`; gửi tin 201 trong 37 ms; đăng nhập 503 kèm requestId; tự hồi phục không restart API |
| `postgres`                          | 10/10   | Có: `/ready` 503, `/health` 200; request cần DB trả 503 trong 10 ms (không phải 500); tự hồi phục                |
| `kafka` (làm ở lần commit trước)    | 14/14   | `dependency_up{name="kafka"}` về 0 rồi về 1; outbox không mất, không đốt `attempts`                              |

Lần chạy Redis đầu tiên **thất bại** ở bước "API khởi động": API cần ~27 giây để sẵn sàng trên máy đang bận, sát ngưỡng chờ 30 giây
của drill; chạy lại khi máy rảnh thì đạt. Tức là ngưỡng đó mỏng trên laptop này, không phải lỗi sản phẩm.

## Khôi phục sao lưu (restore drill)

| Bước                                       | Kết quả                                                                              |
| ------------------------------------------ | ------------------------------------------------------------------------------------ |
| Dữ liệu                                    | DB `ping_demo`: 81 MB, 108.000 tin                                                   |
| `pg_dump -Fc`                              | 695 ms, file 1,1 MB                                                                  |
| `pg_restore` vào container Postgres 17 mới | 3.232 ms                                                                             |
| Đối chiếu `ops/restore-check.sql`          | **giống hệt từng byte** (số hàng và md5 nội dung của 10 bảng, gồm `Message` 108.000) |

Giới hạn: container mới nằm trên cùng máy, cùng Docker, dùng chung đĩa; không phải máy sạch. Dữ liệu nhỏ (81 MB) nên thời gian
**không ngoại suy được** cho DB lớn (bảng 10 triệu tin ở [báo cáo B5](2026-11-17-big-data.md) nặng 6 GB và chưa được dump thử).
RPO/RTO thật của production **chưa đo**: cần sao lưu định kỳ chạy thật và một máy sạch.

## SLO và cảnh báo

Đề xuất SLO và bốn cảnh báo đốt ngân sách ở [slo.md](../runbook/slo.md). Kiểm bằng `promtool test rules` (năm kịch bản mô phỏng).
Chưa có Prometheus/Alertmanager chạy thật.

## Chưa làm

- Staging, và chaos trên nhiều máy (ngắt mạng giữa các node, chết cả instance dưới tải) — không có hạ tầng. Phần gần nhất đã làm là
  SIGKILL một instance API dưới tải trong [báo cáo scale-out](2026-11-17-scale-out.md).
- Restore trên máy sạch, restore DB lớn, đo RPO.
- Cảnh báo đi tới người nhận thật.
