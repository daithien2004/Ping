# Báo cáo hiệu năng — 10 triệu tin nhắn: EXPLAIN, phân vùng, replica (B5, 2026-11-17)

Câu hỏi: khi bảng `Message` lên 10 triệu hàng, truy vấn nóng nào còn nhanh, truy vấn nào gãy, phân vùng bảng và replica đọc
có đáng làm không? ([ADR-0095](../adr/0095-tim-kiem-tu-hiem-tren-bang-lon.md))

## Môi trường

| Mục        | Giá trị                                                                                                                   |
| ---------- | ------------------------------------------------------------------------------------------------------------------------- |
| Máy        | Laptop Intel i5-11400H, Windows 11, Docker Desktop (VM 12 CPU, **3,1 GB RAM**)                                            |
| Dữ liệu    | DB `ping_load`, 10.000.000 tin sinh bằng seed tổng hợp (channel nóng 2.716.577 tin). Bảng + index 6.008 MB, heap 3.113 MB |
| Index      | `(channelId,id)` 851 MB, trgm 748 MB, GIN tìm kiếm 610 MB, pkey 325 MB, unique nonce 169 MB                               |
| Công cụ    | `tools/loadtest/explain.sql`, `explain-b5.sql`, `partition-experiment.sql`, `pnpm --filter api loadtest:replica`          |
| Dữ liệu đo | [data/2026-11-17-b5](data/2026-11-17-b5/) (mỗi truy vấn hai lượt; lượt 1 gần như nguội)                                   |

Hạn chế phải nhớ: nội dung seed là văn bản tổng hợp (không phân phối từ như tiếng thật), VM chỉ 3,1 GB RAM so với bảng 6 GB nên
cache bị đẩy ra liên tục, mỗi truy vấn chỉ có hai mẫu.

## 1. Truy vấn nóng trên 10 triệu hàng

| Truy vấn                                     | Lượt 1 (ms) | Lượt 2 (ms) |
| -------------------------------------------- | ----------- | ----------- |
| Trang đầu lịch sử, channel nóng              | 0,093       | 2,296       |
| Trang sâu (cursor ở giữa 2,7 triệu tin)      | 0,794       | 3,217       |
| Đếm chưa đọc (trần 100), cursor giữa         | 0,978       | 1,058       |
| Đếm chưa đọc, cursor rất cũ                  | 0,172       | 0,267       |
| Tìm từ **phổ biến** (`lorem`, khớp mọi hàng) | 1,127       | 1,342       |
| Tìm từ **hiếm** (`7654321`)                  | **74.562**  | **112.534** |

Phân trang bằng cursor `(channelId, id DESC)` giữ ở mức vài ms dù bảng lớn gấp nhiều lần bản đo trước: đây là kết quả của quy tắc
cursor chứ không phải của phần cứng. Đếm chưa đọc có trần 100 nên dừng sớm.

## 2. Phát hiện: tìm từ hiếm mất 75–112 giây

Truy vấn là đúng SQL của `search.service.ts`: `(search @@ tsquery OR f_unaccent(content) ILIKE '%…%')` kèm
`ORDER BY m.id DESC LIMIT 21` và join `Channel` để ràng buộc `serverId`. Planner chọn `Index Scan Backward` trên `Message_pkey` rồi
lọc từng hàng (`Rows Removed by Filter: 9999999`, 424 nghìn buffer). Lý do: với `LIMIT 21` và ước lượng 49.999 hàng khớp,
đi theo thứ tự `id` trông rẻ (kỳ vọng dừng sau vài trăm hàng); nhưng chỉ có **một** hàng thực sự khớp nên nó quét hết bảng.
Với từ phổ biến thì ước lượng đúng và truy vấn nhanh. Tức là truy vấn hỏng đúng ở trường hợp người dùng hay gõ nhất: một mã hoặc
từ hiếm.

Các biến thể thử trên cùng dữ liệu (`search-variants.out`, một lượt mỗi biến thể):

| Biến thể                                                              | Thời gian           |
| --------------------------------------------------------------------- | ------------------- |
| Gốc (hai nhánh FTS OR ILIKE, `ORDER BY id`)                           | 74.562 – 112.534 ms |
| Chỉ nhánh FTS (bỏ ILIKE), vẫn `ORDER BY id`                           | 78.185 ms           |
| CTE `MATERIALIZED` lấy hàng khớp qua hai bitmap index rồi mới sắp xếp | 301 ms              |
| Thăm dò đếm tối đa 1000 hàng khớp, từ hiếm                            | 8,2 ms              |
| Thăm dò đếm tối đa 1000 hàng khớp, từ phổ biến                        | 0,4 ms              |

Bỏ ILIKE không đỡ: nguyên nhân là `ORDER BY id LIMIT` kéo planner đi theo pkey, không phải nhánh trigram.

Hướng sửa khả dĩ (chưa áp vào code): thăm dò có trần 1000; nếu ít hơn 1000 hàng khớp thì dùng dạng CTE (lấy khớp trước, sắp xếp
sau), nếu nhiều hơn thì giữ truy vấn gốc (đi theo pkey dừng sớm). **Chưa đo** dạng CTE với từ phổ biến: nó sẽ phải vật chất hóa
rất nhiều hàng nên không được dùng không có thăm dò. Chưa đo trên dữ liệu có phân phối từ thật.

## 3. Phân vùng bảng (RANGE trên `id` UUIDv7, 12 phân vùng, mỗi phân vùng ~833 nghìn hàng)

| Truy vấn (lượt 1 / lượt 2, ms) | Bảng thường   | Phân vùng     |
| ------------------------------ | ------------- | ------------- |
| Trang đầu, channel nóng        | 0,093 / 2,296 | 0,804 / 1,679 |
| Trang đầu, channel ít tin      | —             | 1,743 / 6,929 |
| Trang sâu                      | 0,794 / 3,217 | 0,587 / 0,169 |
| Tìm từ hiếm (dạng CTE)         | 301           | 209 / 56      |

Thời gian lập kế hoạch tăng rõ: 8–25 ms ở bảng phân vùng (planner phải xét 12 phân vùng) so với dưới 1 ms thường thấy ở bảng thường.
Không có truy vấn nào nhanh hơn đáng kể vì đã ở mức ms nhờ index cursor.

**Chặn cứng:** khóa duy nhất `(channelId, authorId, nonce)` mà quy tắc idempotency (quy tắc 12) dựa vào **không tạo được** trên bảng
phân vùng theo `id`: `unique constraint on partitioned table must include all partitioning columns`. Muốn phân vùng phải đổi cơ chế
idempotency (ví dụ bảng khóa nonce riêng không phân vùng) — một thay đổi kiến trúc, không phải tối ưu miễn phí.

Kết luận: ở 10 triệu hàng, phân vùng không được biện minh bằng hiệu năng truy vấn; lợi ích còn lại (xóa dữ liệu cũ bằng `DROP PARTITION`,
bảo trì từng phần) chưa cần đến. Không làm.

## 4. Replica đọc (streaming async, hai container Postgres 17 trên cùng máy)

| Phép đo                          | Kết quả                                                                                       |
| -------------------------------- | --------------------------------------------------------------------------------------------- |
| Đọc ngay sau khi ghi (300 lần)   | 0 lần đọc cũ; thấy dòng mới p50 0,62 ms, p95 0,95 ms, max 2,06 ms                             |
| Ghi ~500 dòng/giây trong 20 giây | lag p50 0 byte, p95 8.080 byte, max 17.496 byte; replay lag p50 1,2 ms, p95 4,1 ms, max 30 ms |
| Đợt ghi dồn 200.000 dòng         | primary xong 6.100 ms, replica thấy hết sau 6.212 ms (chậm thêm 112 ms)                       |

**Điều không được rút ra:** hai container trên cùng máy, đi qua loopback ảo của Docker, không có độ trễ mạng thật, đĩa chung. Lag
thật giữa hai máy sẽ cao hơn; số này là cận dưới. Một lần chạy, 20 giây. Mức "0 lần đọc cũ" chỉ nói lag cỡ mili giây, không nói replica
là đọc-sau-ghi an toàn: ứng dụng vẫn phải đọc từ primary với những gì người dùng vừa ghi.
Chưa đo: tải đọc thật chuyển sang replica, failover.

## Chưa làm / chưa đo

- Quét outbox ở quy mô lớn: chưa đo.
- Tìm kiếm trên dữ liệu tiếng thật hoặc với bộ nhớ đủ chứa index.
- Dạng sửa truy vấn tìm kiếm chưa nằm trong code (xem ADR-0095).
