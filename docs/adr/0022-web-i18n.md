# ADR-0022: Web i18n with use-intl, locale chosen in the browser

Status: accepted
Date: 2026-10-20

## Decision

- Library: `use-intl` 4.14.9, the core that `next-intl` is built on. Same API (`useTranslations`,
  `useFormatter`, typed keys) with 4 small dependencies.
- Languages `vi` (default) and `en`. Messages live in `apps/web/messages/{vi,en}.json`, namespaced
  by feature (`common`, `auth`, `app`, `servers`, `channels`, `messages`, `errors`). `vi.json` is the
  source of the key types (`src/i18n/global.d.ts` augments `AppConfig`), so a wrong key fails `tsc`;
  a unit test checks `en.json` has exactly the same keys and no empty values.
- No locale in the URL. The choice is a `locale` cookie read in the browser by `LocaleProvider`
  (`use(browser())`, under `<Suspense fallback={null}>` in `Providers`). Switching writes the cookie
  and reloads the page, which also resets zod's locale, the query cache and pages kept by
  `<Activity>`.
- `LocaleProvider` also sets `z.config(z.locales.<locale>())`, `document.documentElement.lang` and the
  browser's time zone for `useFormatter`.
- Errors: `describeError(error, overrides)` (pure, tested) picks `errors.<ErrorCode>`, a
  caller-translated override, or `errors.unknownWithId` with the requestId; `useErrorMessage()`
  translates it. The server's `message` is never shown.
- Server Components (layouts) show loading text through the client `<Loading />`.

## Reason

`next-intl` reads the locale on the server (`cookies()` in `getRequestConfig`). With
`cacheComponents`, that makes every translated component request-time and requires `<Suspense>`
around each one; next-intl documents no cookie-based setup for Cache Components. The app already
renders only in the browser, so choosing the locale there avoids the problem and keeps server and
client output identical (no hydration mismatch).

## Alternatives considered

- `next-intl` with server-side cookie reading — rejected for the reason above, and it pulls in
  `@swc/core`, `@parcel/watcher` and an extractor plugin we do not use.
- Locale prefix in the URL (`/en/...`) — rejected: no SEO need behind a login; it would move the
  whole route tree under `[locale]`.
- Hand-written `t()` — rejected: plural rules, ICU arguments, date formatting and typed keys are
  what the library gives.

## Consequences

The static HTML has no text (it already had almost none: everything is browser-only).
`metadata.description` in the root layout stays Vietnamese because it is rendered on the server.
The locale is per browser, not per account; storing it on the user needs a migration and an API
change, deferred.
